# 基于实际过程的复盘

## 最困难的问题：确认边界不能交给模型

首批真实冲突案例中，模型观察到 18:00 被占用后主动查询 19:00，但第一次保存将替代时间标成 `WITHIN_FLEXIBILITY`。原始请求其实是硬性时间要求。Guard 返回 `CONFIRMATION_MISMATCH: expected PENDING`，数据库没有接受这次写入。模型在下一轮收到真实拒绝结果后，把状态改成 PENDING，成功保存待确认建议。

这次错误的实际原因是模型把“允许搜索替代窗口”混同于“允许批准替代时间”。工具描述与系统指令虽然说明了区别，仍不足以替代程序约束。解决办法是保留请求不可变、状态白名单校验、精确确认输入和事务内 Guard；没有放宽规则来满足模型输出。原始失败与恢复 Trace 均保留，链接见评估报告。

学到的是：LLM 应负责根据观察选下一步动作，而授权与业务不变量需要由确定性代码独立执行。可以用真实非法动作被拒绝的证据评估安全边界，而不能只看模型最后的自然语言。

## 保存成功必须与事务事实一致

代码将故障注入放在真实 INSERT 之后、COMMIT 之前，以验证回滚。真实保存异常案例中，模型曾自主重试；每次都得到 SAVE_FAILED，最后输出未保存。数据库快照为零行。运行时没有重试逻辑，重试动作来自模型。

唯一键解决重复请求，`BEGIN IMMEDIATE` 解决时段二次检查到写入之间的竞争。测试包含同请求并发只提交一次，以及不同请求并发争抢同一时段只有一次成功。补充了“已查询后插入正式排期”的竞争测试和提交后读库验证失败测试。

## 复现与错误可见性

开发过程中补充了空白标题归一化、模型响应角色校验、预检失败 Trace、数据库验证失败的显式错误，以及源文件哈希快照。它们来自实现检查中的具体缺口，不声称这些缺口曾造成未观察到的生产事故。

本地普通沙箱在 Git 初始化后出现环境刷新启动错误，后续必要验证改为经自动审批的常规命令。最初沙箱内 GitHub 登录检查显示不可用；在可读取系统凭据的执行环境中重新检查，现有账号授权有效。没有要求用户重新提供已有 GitHub Token。

工程测试从首轮 62 项扩展到包含上述边界的最终结果。真实案例、测试输出和验收数字以评估报告为准，不估算成功率，不把模拟器日志当作模型决策。

## 当前限制和下一步

审核只依据合成元数据，不看视频画面，不代表任何真实平台政策；许可补查也是本地合成登记表。真实模型样本数量有限，不能推导总体成功率。CLI 确认没有身份认证，仅适用于本项目的本地可信输入边界。SQLite 适合单机验证，正式调度系统和过期草稿清理未实现。

下一步有直接价值的改进是：引入独立持久化素材版本与审核证据版本、扩大真实决策样本并统计重复运行稳定性、给草稿增加明确失效策略，以及在真正业务集成前补充认证与确认来源验证。当前项目没有接入真实发布接口的计划。
